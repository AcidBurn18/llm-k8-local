# Known Limitations and Production Readiness Roadmap

## Scope

This repository is a local DevSecOps assessment that runs on Kind. It demonstrates useful infrastructure and security practices, but the `prod` environment name does not make the Kind cluster a production platform. The production root has not been deployed or verified against a real cloud account or an organization's standards.

This document separates what is already present from what is incomplete or has not been demonstrated. “Not demonstrated” is different from “does not exist”: a manifest may be present while its behavior still needs a runtime test.

## Current state and gaps

| Area | Present in this assessment | Limitation and recommended implementation |
|---|---|---|
| **Secrets** | A Kubernetes Secret manifest is checked in at [`infra/k8s/secrets/app-secrets.yaml`](../../infra/k8s/secrets/app-secrets.yaml). Its API key is explicitly a demo placeholder; the model checksum is configuration data. The Grafana admin password is set inline in [`helm-prometheus.tf`](../../infra/terraform/modules/platform/helm-prometheus.tf). | Do not put real credentials in YAML or Terraform source. For a cloud deployment, store secret values in the organization's approved manager, such as HashiCorp Vault or Azure Key Vault. Give the deployment identity access using workload identity/OIDC, then expose only required values to Pods using the External Secrets Operator or Secrets Store CSI Driver. Kubernetes Secret objects may still be created, but they are delivery objects, not the source of truth; enable encryption at rest and restrict RBAC. Avoid reading secret values into Terraform when possible because sensitive Terraform values can still be present in state. For local development, use a documented local-only mechanism and non-production credentials. |
| **CI/CD and GitHub integration** | The [`Makefile`](../../Makefile) has local `check` and `release` flows for linting, tests, image builds, SBOMs, Trivy scans, Terraform, and Kubernetes deployment. | No GitHub Actions workflow or `.github/CODEOWNERS` file is present in this checkout. Keep the Makefile as the reusable local interface; have GitHub Actions call its non-interactive checks. Add separate pull-request validation and protected deployment workflows, plan artifacts, environment approvals, and OIDC authentication to cloud services instead of long-lived cloud keys. Ensure destructive Terraform actions require an explicit protected-environment approval. |
| **Terraform state** | `dev` and `prod` have separate root directories and therefore separate local state locations. Both call the shared platform module. | State is local, so it is not centrally protected, shared safely by a team, or reliably locked. Configure an approved remote backend (for example, HCP Terraform/Enterprise or the cloud provider's state service) with encryption, access controls, locking, versioning, and a separate state key/container per environment. Restrict production state access to the deployment identity and authorized operators. Back up existing state and plan a controlled migration before changing backends. |
| **Repository ownership and change control** | These controls are not defined in the checked-in application and infrastructure files. | Confirm the actual GitHub repository owner and organization, then configure branch rules or rulesets, required reviews and checks, protected deployment environments, and secret/push protection. Add `CODEOWNERS` for Terraform, Kubernetes, and application paths. Repository-level permissions and rules must be verified in GitHub; a file in this repository cannot enforce all of them by itself. |
| **Images and vulnerability response** | Images are built locally and scanned by Trivy; SBOMs and scan reports are generated. The scan gate fails on HIGH/CRITICAL by default, but `ALLOW_HIGH_VULNS=true` can bypass the gate. The documented scan results include HIGH and CRITICAL findings. | Scanning is implemented; the missing work is a repeatable remediation and release policy. Triage each finding for affected component, exploitability, and available fix; update base images and dependencies; record approved exceptions with owner, rationale, and expiry. Do not use the override as a production release path. For hosted releases, push immutable image digests to an approved registry, promote the same digest between environments, and add provenance and image signing/verification. The local `v1` tag and Kind image loading are suitable for the demo, not a release strategy. |
| **Terraform platform standards** | A shared `platform` module is called by the two environment roots. Some variables already have descriptions and validation blocks. | Establish organization conventions for resource/module naming, required tags/labels, variable types and descriptions, validation, output descriptions, provider and module versioning, and generated documentation. Add consistent `terraform fmt -check`, `terraform validate`, provider security/lint checks, and plan review to CI. Split the shared module into smaller modules only when ownership or lifecycle boundaries justify it; avoid creating modules that merely wrap one resource. |
| **Cloud network foundation** | Kind maps local host ports to a single Docker-backed control-plane node. Kubernetes NetworkPolicy manifests describe intended service paths. | There is no cloud VPC/VNet foundation here. Design this with the target organization before deployment: address ranges, environment segmentation, private/public subnet tiers, routes, egress controls, private endpoints, cluster/API access, DNS, load balancers, and firewall/security-group rules. Keep the Terraform state backend's network access and identity controls as a separate design item from application VPC/VNet networking. Choose a CNI or policy engine that enforces the policies, then prove both allowed and denied traffic paths. |
| **DNS and ingress** | The local environments use `llm-app.local`; distinct host ports select dev or prod. Local TLS is based on mkcert. | Port selection is a laptop workaround, not environment isolation for real users. Use environment-specific DNS names or delegated zones, managed certificates, and an approved ingress/load-balancing design. Keep production endpoints and credentials separate from development. Verify certificate trust and routing without `curl -k` before calling the path production-ready. |
| **Kubernetes availability and scaling** | The platform includes a gateway HPA and PDB, and Metrics Server resource metrics have been observed in Kind. | Kind is a single-node development cluster. A PDB cannot provide node-level availability there, and HPA configuration alone does not prove scaling works. Only dev has been exercised; the prod root is still a local example. For a real environment, use an appropriately sized managed or supported multi-node cluster, capacity planning, resource requests/limits, autoscaling policies, topology spread, storage classes, upgrade procedures, and tested disruption behavior. Run a load test and demonstrate scale-up and recovery. |
| **Monitoring and alert response** | Prometheus and Grafana are installed. The chart supplies general Kubernetes rules; [`infra/k8s/alertrule.yaml`](../../infra/k8s/alertrule.yaml) adds gateway error-rate and failed-Job alerts. | Rule loading/evaluation has been observed locally, but that does not prove an incident workflow. Configure an approved alert destination and ownership, then test a controlled failure through firing, notification, acknowledgement, and resolution. Add service-level objectives, actionable runbooks, retention requirements, and alert-noise review. Keep the distinction between upstream cluster rules and the small set of application-specific rules clear. |
| **Backup and recovery** | The model weights are stored on a PVC; Terraform state is currently local to each root. | There is no demonstrated backup/restore or disaster-recovery procedure. Define recovery objectives, identify data that must survive cluster loss, back up state and required persistent data, and periodically test restoration into an isolated environment. Document recovery credentials and access paths separately from the systems being recovered. |
| **Validation and operational proof** | Python unit tests, smoke checks, image scans, and a Terraform plan/apply flow exist. | Add infrastructure-focused checks and record evidence for the important runtime behaviors: NetworkPolicy deny tests, alert firing and notification, CronJob success/failure handling, HPA scale-up, deployment rollback, and state recovery. A successful plan or a present manifest is not proof that the behavior works. |

## Suggested implementation order

1. **Before any cloud deployment:** choose the target cloud and organization network/IAM standards; remove inline credentials; create protected remote state with separate dev/prod access.
2. **Make changes reviewable:** add repository ownership/rules and GitHub Actions that reuse the Makefile, publish Terraform plans, and require approval for production.
3. **Make releases traceable:** triage and remediate Trivy findings, publish immutable image digests, and add provenance/signing and controlled promotion.
4. **Build the runtime baseline:** provision the approved network and managed Kubernetes platform, then configure environment DNS/TLS, workload identity, policy enforcement, and capacity.
5. **Prove operations:** test alert delivery, failure recovery, backups, autoscaling, and rollback; document runbooks and ownership before labeling the environment production-ready.
6. **Standardize as the platform grows:** enforce Terraform naming, tagging, validation, documentation, versioning, and security checks through reusable module conventions and CI.
