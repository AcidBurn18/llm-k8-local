# AI Usage Disclosure

I used AI assistants during this assessment: Claude earlier in the work and OpenAI Codex during later implementation review, troubleshooting, and documentation. AI contributed to drafts and revisions of some code, Kubernetes and Terraform configuration, tests, and documentation. I do not claim that every line was written without AI.

I worked iteratively: I brought requirements, failures, and design questions; AI helped analyze selected code and propose changes; I chose what to keep and checked important conclusions against repository and deployment evidence. I did not use one prompt to generate a finished assignment. The efficiency came from asking AI to correlate related files and evidence quickly, surfacing gaps that are easy to miss in a time-limited manual review. I still had to validate the findings and understand the trade-offs.

## Examples of focused AI-assisted analysis

| Question or problem I brought | What AI helped trace or challenge | My decision and how I checked it |
|---|---|---|
| **Does `ENV=prod` really isolate Terraform from dev?** | Traced the selected environment variables separately from Terraform's state location. A different tfvars file or Kind cluster name does not itself select a different state. | I chose separate `infra/terraform/environments/dev` and `prod` roots that call the shared platform module. The roots now have separate local state locations; a protected remote backend and locking remain future work. |
| **Why did teardown report a missing `kind-dev` context?** | Analyzed the dependency between the Kind cluster resource and the Helm/Kubernetes providers, including which API endpoint and kubeconfig context those providers use during normal apply versus destroy. | The implementation has an explicit `destroying_kind` path that selects `kind-${var.env_name}` from kubeconfig during teardown. I learned to check whether the cluster/context exists and to reason about provider configuration across resource destruction, rather than treating `ENV=dev` as proof that the context is available. See [`providers.tf`](../infra/terraform/modules/platform/providers.tf) and the [`destroy` target](../Makefile). |
| **Could the model health-check Job be blocked by NetworkPolicy?** | Compared the Job's pod labels, the assistant destination, DNS egress, and the actual policy ports before proposing a change. The policy comments mention port 8000, while the active manifest and service path use 8005. | I did not treat a timeout as proof that a new allow rule was needed. The correct diagnosis is to inspect the running Job labels, Service endpoints, logs, applied policies, and whether the CNI enforces NetworkPolicy. A manifest in the API is intent; a controlled allowed-and-blocked traffic test is needed to prove enforcement. See [`cronjob.yaml`](../infra/k8s/cronjob.yaml) and [`network-policies`](../infra/k8s/network-policies/). |
| **Why were the custom Prometheus rules missing?** | Compared the `PrometheusRule` labels with the Helm release/Prometheus selector instead of assuming the PromQL was invalid. The release label did not match the monitoring release. | The label was aligned to `release: monitoring`. I then checked Prometheus' Rules page and confirmed `GatewayHighErrorRate` and `CronJobFailed` were loaded and evaluating (`OK`). That verifies rule discovery/evaluation, not that an alert fired or reached an incident channel. See [`alertrule.yaml`](../infra/k8s/alertrule.yaml). |
| **Are pinned Terraform provider versions a security control?** | Used AI as a reviewer to separate reproducibility from security: a version constraint limits unexpected upgrades, but does not establish that a provider is trustworthy, current, or safely configured. | I used the analysis to understand the provider source addresses and version constraints, and treated pinning as one control rather than a security verdict. A stronger team process would review provider sources, commit the dependency lock file, update deliberately, scan IaC, and review plans under least-privilege CI identity. |
| **Do Kubernetes Secrets or a Trivy override resolve the underlying risk?** | Challenged two common false conclusions: Base64 in a Kubernetes Secret is not encryption, and letting a scan continue is not remediation. It also surfaced the inline Grafana password in Terraform and distinguished it from the checked-in demo API-key placeholder. | I documented secret-manager integration as future work and left the Trivy findings visible. `ALLOW_HIGH_VULNS=true` allows the local release to continue; it does not fix or suppress the HIGH/CRITICAL findings. Those need triage, fixes, or a time-limited, owned exception before promotion. |
| **What is the difference between Metrics Server and Prometheus?** | Connected each component to its actual use in this cluster: Metrics Server serves the Kubernetes resource metrics API for `kubectl top` and HPA; Prometheus scrapes application and monitoring metrics for queries, dashboards, and alert rules. | I used `kubectl top` and the browser interfaces to inspect the running system. I did not describe a Grafana dashboard as proof that HPA scaling, alert delivery, or every scrape target worked. |

These examples show the way I used AI: provide a concrete symptom or disputed claim, ask it to trace the relevant implementation, then verify the proposed explanation against code or observable behavior. AI reduced the time spent searching across files and generating hypotheses; it did not make verification unnecessary.

Representative questions included:

- “Trace which Terraform state and working directory `make infra ENV=prod` actually uses. Do not infer isolation from the environment name or tfvars file.”
- “For this destroy-time Kind error, trace the `kind_cluster` and Kubernetes/Helm provider lifecycle. Explain which kubeconfig context the provider needs and what evidence distinguishes a missing cluster from a provider configuration problem.”
- “Review the health-check NetworkPolicy path using the pod labels, DNS rule, Service port, and policy port. Do not suggest widening access until the active rule and runtime path are checked.”
- “Does pinning a Terraform provider version make this infrastructure secure or only reproducible? Identify the remaining supply-chain and privilege risks.”
- “Compare the PrometheusRule labels with the Helm release selector, then tell me how to verify discovery and evaluation in Prometheus.”

## AI-assisted implementation and writing

AI also helped draft or revise parts of the FastAPI services, error handling, unit tests, Dockerfiles, Kubernetes resources, Terraform/Helm configuration, Makefile workflows, and submission documents. I reviewed the resulting changes and retained responsibility for the design choices and claims. For example, the Makefile still requires explicit approval before Terraform apply, the scan reports remain available when the local severity gate is overridden, and known gaps are described as gaps rather than completed controls.

The separate [known limitations and production readiness roadmap](docs/known-limitations-and-production-roadmap.md) was prepared with AI assistance from the repository and assessment context. I reviewed it to distinguish implemented controls from incomplete or unverified behavior, including the fact that the `prod` root is still a local Kind example.

## Verification and limits

- The recorded local release ran Ruff and the service tests; the last recorded test run passed 27 tests. The release also built four service images, generated SBOMs, ran Trivy, applied resources, and completed the recorded smoke checks. These are assessment results, not proof of production readiness.
- Metrics Server returned node and application pod metrics. The two application Prometheus rules were confirmed loaded and evaluating. HPA scale-up under load, alert notification to an incident channel, NetworkPolicy enforcement, CronJob failure handling, browser certificate trust, and recovery from a real node failure were not established by those checks.
- Trivy reports include HIGH findings and a CRITICAL finding in the LLM image. The reports remain part of the deliverable; reviewing them with AI did not close the findings.
- I compared important AI explanations with source files and runtime output. Where behavior was not observed, I recorded it as unverified or as a future implementation item rather than presenting a plausible explanation as evidence.
